# Coordinated toolchain updates

Sadoc should propose upgrades to the tools a repository builds, tests, and ships with. Each PR updates one coordinated toolchain set. A set includes all pins for the same toolchain installation and any other tools that must move with it. Independent sets get independent PRs.

## Approaches

A repository-wide PR would cover every toolchain in one run, but an unrelated failure could block an otherwise ready upgrade. Independent proposals per file would be easy to retry, but could leave CI, developer machines, and images on incompatible versions. The selected approach groups pins by project and toolchain, then joins sets that share an edited file or require a compatible joint upgrade.

## Discover the pins and their roles

Scan tracked build inputs across the tree, including workspace manifests, version files, mise and asdf configuration, CI workflows and matrices, Dockerfiles, Compose and devcontainer configurations, and supported literal install and bootstrap commands. Cover runtimes, compilers, package managers, and build tools through parsers that record the tool, scope, role, file, and existing pin. Support repository declarations for custom pin locations and coordination boundaries, using validated file paths and explicit version locations.

Cover the conventional pin forms used by Node and npm, Yarn, pnpm, and Bun, as well as Python, Go, Rust, JVM tools, Ruby, PHP and Composer, Swift, Dart, and Erlang and Elixir. Document supported forms for each. A failed read of a build input in scope, an ambiguous project boundary, or a recognized toolchain reference with an unresolved expression blocks the affected set until Sadoc can read or resolve it. Report the location and allow an explicit repository mapping to resolve it. Arbitrary code can hide pin references, so declare supported forms and allow repositories to map custom locations.

Track compatibility requirements and intentionally different environments separately from installation pins. A project runtime and its corresponding CI, development, and shipping pins move together. A supported-version floor, MSRV, compatibility range, or older matrix lane retains its role unless the repository explicitly identifies it as a coordinated install pin. A workflow that reads a shared version file picks up the change through that file.

## Choose a release

Resolve exact versions from authoritative release metadata or registries. Default to the newest supported LTS line where the publisher designates one, and the newest stable release elsewhere. Honor repository policies that restrict a toolchain to its current release line and select the newest eligible bug-fix release within that line. Exclude prereleases and nightly releases by default. Preserve pin precision, channels, image variants, and platform requirements. A floating major pin already receives compatible patches through the installer. Update it only when the selected release changes the rendered major or when an exact pin elsewhere deliberately anchors the installation. If multiple pin forms cannot express compatible targets, report the mismatch. Verify any transformed artifact reference, including image tags and digests, and validate compatibility with other pinned tools. If a dependency migration identifies a toolchain blocker, use that diagnosis to prioritize the prerequisite proposal. Version and artifact selection stays in deterministic code. Use one classifier for workflow runtime detection and for artifacts such as Docker images. Once a reference belongs to a toolchain set, the ordinary dependency pass suppresses the duplicate even when the toolchain set is blocked.

## Group and verify

Join matching pins across files, then join sets with overlapping edit footprints such as a shared manifest or lockfile, or a verified compatibility requirement. Keep intentional independent installations in the same monorepo distinct even if they use the same tool. Give each set an identity based on its project scope and tools, independent of the target release, and persist its file footprint. Reuse or defer an open proposal for that set across scans. Allow independent, non-overlapping sets to proceed in parallel. An existing open PR reserves its edit footprint. Do not open another proposal that edits those files. Rescan when the existing PR lands or closes. When planning new work, prefer toolchain sets over overlapping routine dependency updates. A toolchain set that cannot produce a PR does not reserve files. Give overlapping security fixes priority when they verify on the current toolchain. If an open toolchain PR already holds the files, surface the conflict so the maintainer can choose which PR takes precedence.

Apply the planned pin changes together and regenerate derived artifacts with the selected toolchain. Reparse changed files and check all expected pins against the plan before publishing. Persist the selected versions and expected pins with the PR so the same check can run after migration, CI repair, conflict resolution, or review edits. Use the stored plan for all PR maintenance and merge decisions. If a toolchain proposal has no recoverable plan, block further writes until it is rescanned. A changed base that alters the set requires a fresh scan and validation before further pushes. A missing required pin, unexpected toolchain edit, unavailable release artifact, or failed verification blocks the whole set and produces a diagnostic that identifies the file or check.

Discover and replay verification from a disposable snapshot of the proposed tree using the selected toolchain versions. The recipe fingerprint and discovery reset point must use that snapshot. Include toolchain pin files in recipe fingerprints. Preserve immutable lockfile checks. Reuse the existing sandbox and orchestrator ownership of GitHub writes. Toolchain sets require review regardless of bump size or dependency auto-merge settings.

## Acceptance

A checked-in synthetic fixture modeled on the icod2 failure should yield one Yarn proposal covering the root and workspace pins, the Docker bootstrap, and lockfile regeneration. Additional integration cases should prove that one runtime update reaches its version files, CI and container pins, an older test lane retains its purpose, independent sets get separate PRs, and a missing artifact or partially applied set produces no PR. Verify through the normal scan, state, and PR pipeline, including persisted records from before toolchain support.
